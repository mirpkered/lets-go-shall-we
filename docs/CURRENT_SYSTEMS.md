# Current Systems

This is a code-checked summary of the implementation on `main`. For scenario-level inventories and audit limits, see [Adventure Library Status](ADVENTURE_LIBRARY.md) and the [ending/reward audit](LIBRARY-ENDING-REWARD-AUDIT.md).

## Play and persistence

- **237 registered adventures**, selected with soft risk-tier weighting. Normal play has no scenario picker. Selection excludes up to the five most recently ended scenarios; if that would empty a small eligible pool, the exclusion window is reduced until a choice exists. Traveler completion count and the latest eight completed/death risk tiers influence only selection weights; abandonment still enters scenario-repeat history, while QA uses a separate save and never changes player history.
- The internal LOW / MODERATE / HIGH / SEVERE classification describes authored consequences, not genre. Selection uses no fixed cadence and does not scale a selected story’s odds, enemies, or character stats. Full library assessment: [Scenario Risk Audit](SCENARIO-RISK-AUDIT.md).
- Adventure scenes are forward-only narrative moments. Scene visits, run-level randomized names/selections, flags, inventory, health, money, fictional elapsed time, and relevant event state are persisted for exact resume.
- Fictional time advances only through authored player choices. The UI does not advance it while reading or while the browser is closed.
- A living character starts at 10/10 health, may acquire character-specific history, lore, knowledge, money, and gear, and can die or be voluntarily retired. Death, retirement, and abandonment end that character; the persistent Bank is separate.
- Local browser storage is the save system. There are no accounts, cloud saves, multiplayer, or server-side gameplay. Save schema is still version 1; `src/storage.ts` applies safe defaults and targeted legacy migrations, including the legacy single-item carry alias and visited-scene/progression reconstruction.
- Four choices use the phone-oriented 2×2 grid; the interface adapts for fewer choices. The app includes Mirpworks launch splash, title-screen scene rotation, gameplay HUD, About, Contact & Feedback, Bank, reward placement, and retirement flows.

## Traveler continuity, rewards, and Bank

- Persistent carryables are divided into **40 Gear items and four Relics**. Starting Small Knife and Lantern are run Gear, not persistent carry rewards. Gear uses the traveler’s 1/2/3 Gear capacity; Relics are listed separately, are not hard-capped, and do not consume Gear slots.
- Three prototype Supply types use character-bound quantity stacks: Ritual Chalk (4), Consecrated Salt (3), and Cold-Iron Nails (6), with room for four distinct Supply types. They cannot be banked and are lost with the traveler. Character Assets remain separate; temporary equipment remains run-only.
- Carryable gear state is stored separately by stable item ID: `NORMAL`, `DAMAGED`, or `BROKEN`, plus named item-specific upgrades and provenance. Old saves default safely to sound gear with no upgrades. Broken gear remains owned but is not usable for authored equipment checks. Wear is only applied by explicit story events; there is no passive durability system. Bank deposit/withdrawal preserves the record, death/retirement discard unbanked gear state, and an ending counts a changed persistent carried item toward traveler progression.
- A traveler has one Gear slot at 0–9 qualifying completions, two at 10–19, and three at 20+. An authored ending advances the count when explicitly substantive or when persistent carried items, their condition/upgrades, Supply rewards, or currency changed over the run; transition count is diagnostic only. QA and explicit abandonment do not count. The newly unlocked slot is available on the next adventure. Count resets with that traveler’s death, abandonment, or retirement; no stat levels or account progression exist.
- Character-bound owned property is tracked separately from inventory and the five-item Bank. It is visible under Owned property, uses no carried slot, and is cleared with that traveler.
- The Bank stores persistent Gear and Relics only, survives death and character changes, and has a nominal capacity of **five**. Supplies, lore, knowledge, money, history, and Assets cannot be banked. Existing legacy over-capacity contents are preserved; deposits stop until space is made. Players can withdraw, swap, discard one item, or empty the Bank with explicit confirmation. Disposal is intentional and irreversible.
- At authored endings, a named persistent item reward can be carried (within capacity), deposited directly into available Bank space, or explicitly declined. Choose-one rewards remain exclusive. Full carry plus full Bank never silently overwrites or discards an item. Ending reward placement is not general Bank management.
- Money, lore, knowledge, and history belong to the living traveler. They are not bankable and are lost when that traveler is lost. Authored outcomes may grant wages, money, gear, information, history, relationships, or a quiet narrative payoff; not every adventure grants material reward.

## Randomization and optional incidents

- Normal selection is a two-stage weighted draw: evenly sample eligible primary activity categories, with soft category-recovery pressure from the living traveler’s last eight starts, then weight scenarios within the selected category by long-run/recent risk pressure, seasonal and historical-presence modifiers, and a strong nonzero per-traveler replay penalty. Out-of-season adventures are excluded first; the latest five ended/abandoned scenario IDs are then excluded where possible, relaxing only the oldest exclusions if necessary. Category history and authored-ending play counts are per traveler and migrate to empty for legacy saves; exact recent scenario IDs remain device-level. Easter-egg history stays separate. Current seasonal assignments include four earlier winter/spring/autumn/December stories, four October-locked Halloween stories, and eight ALL_YEAR stories with an October-only 1.35 affinity boost. Active runs and persistent rewards survive month changes. `?qa=1` offers a month override, direct launch, selection diagnostics, and isolated 100/1,000-draw simulation in addition to the diversity report. See [Scenario Diversity](SCENARIO-DIVERSITY.md).
- A complete diversity metadata row is available for every **237 registered adventures**, combining cautious legacy content classification with explicit author overrides. Dimensions include role, activity, structure, tone, setting, risk, fantasy density/threat, combat, length, entry, outcome, reward, consequence, seasonal availability/affinity, and distinctive hook. Similarity and repeated scene/choice-shape checks are warnings for human review; expensive audits are never part of normal Begin Adventure selection.
- The QA panel also offers an on-demand content-substance report. It reviews reachable terminal routes for short obvious-action, procedural, agreement, wager, task/performance, and payoff warning patterns, with evidence and suggested review. These heuristics are warnings only, overlap by route, and do not block release; the report includes structural pattern warnings from the diversity framework so authoring can be reviewed together.
- Run-level NPC name selections are chosen at run start and saved; reload does not reroll them.
- Conditional incidents and time-aware text are authored in scenario data. Rare Easter eggs have a **2% per eligible scene-entry chance**, at most one per run, a local recent-seen list, and no gameplay, reward, knowledge, history, or progression effect. They do not establish crossover canon.
- Five title-screen illustrations are selected per browser session, with QA previous/next preview. The current SVG scenes are recognized as too subdued/abstract to read as five distinct illustrated destinations. A richer art pass and cross-session repeat prevention remain future work; the framework itself is implemented.

## Content substance review snapshot

The first on-demand quality audit reviewed **809 terminal routes across 175 adventures** (2026-10-01). It produced 0 HIGH, 151 MEDIUM, and 426 LOW warning records. Warning categories overlap: 72 obvious-action, 55 procedural, 0 one-wager, 2 agreement, 94 routine-task, 94 performance-feedback, and 260 possible no-visible-payoff notices. LOW/MEDIUM notices intentionally include false positives, particularly short peaceful vignettes and generic but satisfying outcomes; inspect each route rather than treating the totals as defects. The audit is a triage aid, not a score or hard gate.

## QA and public/shared services

- `?qa=1` reveals direct launch for each registered scenario, explicit HIGH/SEVERE quick launches, current risk tier, recent risk history and next-selection tier weights, plus state inspection (scenario, scene, visited IDs, inventory classes, Gear, Relics, Supply quantities, owned Assets, item condition/upgrades/provenance, flags, money, health, history, lore, knowledge, Bank, time, progression, recent selections, and Easter-egg state); clear-run; reset-character; clear-QA-save; set health/time/completion count/Gear milestone; force add/remove Gear or Relics; set/add/consume persistent Supplies; test equipment condition, break/repair, add/remove upgrades; Easter-egg preview/toggle; and home-art preview. Normal play has none of these controls. QA uses a separate local key and suppresses progression/counter accounting.
- The anonymous global Adventure Counter targets the existing Cloudflare Worker **`dark-scene-308e`** through `counter-service/wrangler.jsonc`. It uses one `COMPLETION_COUNTER` binding to the `CompletionCounter` SQLite Durable Object (`new_sqlite_classes` migration `v1`); there is no D1 database, KV namespace, or separate service. SQLite stores only a singleton aggregate total and unique opaque run UUIDs; an insert trigger increments once for each new UUID. The Worker accepts only `GET /v1/total` and `POST /v1/complete` with exactly `{ "runId": "<UUID v4>" }`, limits the payload to 128 bytes, and allows the GitHub Pages origin plus localhost development origins. This is basic abuse resistance, not authentication; the total is anonymous and not tamper-proof.
- The browser client is enabled only when production build variable `VITE_GLOBAL_COMPLETION_COUNTER_URL` is set to the deployed Worker’s HTTPS base URL. It displays a returned real total on the home screen and hides the count on endpoint failure—never inventing zero or a seed. Normal authored terminal outcomes count, including success, death, and authored walk-away; explicit abandonment, unfinished/closed runs, and QA runs do not. Successful-run submissions queue only after reward resolution, death submissions queue after the persisted death ending, and both use the stable run UUID. Local state is saved before network submission; failure never blocks an ending and pending IDs retry on a later load. Duplicate requests are harmless. Normal players see only the aggregate; the QA inspector shows endpoint configuration, current total, run ID/status, pending count, and last request result.
- **Production activation remains pending:** the Worker name has been aligned to the manually created `dark-scene-308e`, but Cloudflare deployment credentials were unavailable during setup. No exact `workers.dev` subdomain or live total has yet been verified. To activate it, add GitHub Actions repository secrets `CLOUDFLARE_API_TOKEN` (Workers edit/deploy permission, scoped to this Worker if Cloudflare permits) and `CLOUDFLARE_ACCOUNT_ID`, then run the existing “Deploy global completion counter” workflow on `main`. Use the deployed Worker’s reported `workers.dev` base URL as `VITE_GLOBAL_COMPLETION_COUNTER_URL`, rebuild the static client, and publish that build to `gh-pages`. Do not send the API token in chat. No custom domain is configured or required.
- Hosting is static GitHub Pages under `/lets-go-shall-we/`; no backend is required for play. The optional counter is the only service component and does not host gameplay or saves.
